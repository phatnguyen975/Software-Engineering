# File Conventions — wat-build

Naming, placement, and creation rules for all files generated by this skill.

## File Naming

| File type         | Pattern                     | Examples                     |
| ----------------- | --------------------------- | ---------------------------- |
| Page Object Model | `{feature}.page.ts`         | `register.page.ts`           |
| Feature fixture   | `{feature}.fixture.ts`      | `coupon.fixture.ts`          |
| Spec file         | `fr-{xx}-{feature}.spec.ts` | `fr-01-registration.spec.ts` |

**Rules:**

- All names use kebab-case.
- `{feature}` is the short, lowercase name of the feature (not the FR number).
- `base.page.ts` and `base.fixture.ts` are pre-existing base files — never overwrite them.

## File Placement

```
{E2E_DIR}/
├── pages/
│   ├── web/          ← POM files for frontend-web features (user-facing)
│   └── admin/        ← POM files for frontend-admin features
├── fixtures/
│   └── *.fixture.ts  ← Feature fixtures (base.fixture.ts is the entry point)
└── tests/
    ├── web/          ← Spec files for frontend-web features
    └── admin/        ← Spec files for frontend-admin features
```

**Routing rule:**

- Features where the primary actor is an unauthenticated or standard user → `web/`
- Features where the primary actor is an admin user → `admin/`

## When to Create a Feature Fixture

Create a `{feature}.fixture.ts` when **at least one** of the following applies:

| Condition                                                                               | Why a fixture is needed                                  |
| --------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Tests require data created via API before each test                                     | API calls need setup/teardown lifecycle                  |
| Tests require data deleted via API after each test (cleanup)                            | Teardown code after `await use()`                        |
| Multiple test files for the same feature share the same page object lifecycle           | Fixtures are composable; `beforeEach` in spec is not     |
| The precondition involves navigating through multiple pages to reach the starting state | Encapsulate the navigation chain in one reusable fixture |

Do **not** create a feature fixture when:

- `beforeEach` with `new PageObject(page)` and `goto()` is sufficient.
- The feature is unauthenticated and requires no precondition data.

## Registering a New Fixture

After creating `{feature}.fixture.ts`, register it in `fixtures/base.fixture.ts`:

```typescript
// Before (base.fixture.ts)
export const test = base.extend<AuthFixtures>({ ...authFixtures });

// After — add import and merge
import { cartFixtures, type CartFixtures } from "./cart.fixture";
export const test = base.extend<AuthFixtures & CartFixtures>({
  ...authFixtures,
  ...cartFixtures,
});
```

All spec files that use the fixture continue to import from `@fixtures/base.fixture` — no change needed in spec files.

## One POM per Page/Screen

Create a separate POM class for each distinct page or screen the feature interacts with. If a feature spans two pages (e.g. registration form → login redirect), create two POM classes.

Do not create a single "god" POM that wraps the entire application.
