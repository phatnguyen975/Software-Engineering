## Part 1 — Purpose

This usability test evaluates the **event management workflow** for admin users on the EMS (Event Management System) of the Faculty of Information Technology, HCMUS. The test covers the end-to-end admin journey: discovering the event list, creating and publishing a new event, then reviewing and approving participant registrations.

The test will inform:

- Whether first-time admin users can complete the full event lifecycle without assistance.
- Which specific UI elements or flows in screens A1, A2, and A4 cause the most friction.
- Whether the form design on A2 (image uploads, Rich-Text editor, date/time pickers) is learnable without training.
- Whether the status management interface on A4 (Registrants, Review Lecturers, Review Students tabs) is interpretable without prior context.

Results will be used to produce a **Usability Report** and to generate concrete improvement recommendations for the EMS team.

## Part 2 — Problem Statement

The following research questions must be answered by this test:

1. Can a first-time admin user locate where to create a new event and initiate the creation process without guidance?
2. Can a first-time admin user correctly fill in all required fields in the Add Event form — including the thumbnail (4:3) and banner (24:9) image uploads, the Rich-Text description, and the date/time constraints — without instruction?
3. Does the user understand the difference between "Save as Draft" and "Publish," and can they successfully publish the event on their first attempt?
4. After publishing, can the user navigate back to the Event List and verify that their event appears with the correct published status?
5. Can a first-time admin user navigate to the Participants section of a specific event and correctly interpret the registration status of each registrant (e.g., `PENDING`, `APPROVED`, `WAITLISTED`)?
6. Can the admin successfully take approval actions on registrations, and do they understand what happens after approving or rejecting a registrant?
7. Can the admin locate and successfully use the Export function to download the participant list?

## Part 4 — User Profile

### Target Profile

Faculty staff of a university (lecturers, department admins, academic affairs officers) who:

- Are comfortable with general web-based admin tools (e.g., Google Workspace, LMS systems, university portals).
- Have no prior experience using the EMS system.
- Have basic familiarity with the concept of academic events (workshops, seminars, conferences).

### Inclusion Criteria

- University faculty member, graduate student (Year 3+), or university administrative staff.
- Uses web-based productivity tools regularly (at least 3–4 times per week).
- Has not used the EMS system before this session.
- Is willing to think aloud during the session.

### Exclusion Criteria

- Current or former users of the EMS system (any role).
- Members of the testing/development team.
- People with no web browser experience.

### Recruitment Method

Personal network (colleagues, classmates outside this course, department staff). Participants must be recruited individually and will each receive a unique session file.

### Number of Participants

**5 participants** — consistent with Nielsen's (2000) finding that 5 users uncover ~85% of usability problems in a task-based assessment test.

## Part 5 — Method & Test Design

- **Test type:** Assessment (mid-stage; product is functional, concepts fixed)
- **Session format:** Moderated
- **Design:** Within-subjects — all 5 participants complete the same single task (T1)
- **Number of participants:** 5
- **Pilot session:** 1 additional pilot participant (not counted in the 5), conducted before main sessions to validate the task scenario and session logistics
- **Estimated session duration:** 30–40 minutes
  - Pre-task briefing: 5 min
  - Think-aloud practice task: 3 min
  - Main task T1 (benchmark 12 min, allow up to 20 min): 20 min
  - SUS questionnaire: 3 min
  - Probe questions debrief: 5–7 min
  - Total: ~35 min

## Part 7 — Test-Monitor Role

### Before the Session

- Set up the browser with the starting screen (A1 — Event List) visible and the admin account already logged in.
- Prepare the session notes file (`P{n}-session.md`) with participant ID filled in.
- Prepare a think-aloud warm-up task (unrelated to EMS, e.g. "Imagine you are on a news website — tell me what you're thinking as you decide which article to read").
- Brief the participant:
  - _"We are testing the system, not you. There are no right or wrong answers."_
  - _"Please think aloud — say whatever comes to mind as you work."_
  - _"I cannot answer questions about what to do, but I will let you know when to stop."_

### During the Session

- **Neutral observation only.** Do not nod, react, or comment on participant actions.
- Use only these permitted prompts:
  - Think-aloud reminder: _"What are you thinking right now?"_
  - Neutral clarification if participant asks a question: _"What would you expect to happen?"_
- **Intervention threshold:** If the participant has been completely stuck and silent for **more than 5 minutes** with no progress, note the timestamp, mark as intervention, and say: _"Let's move on. I'll note that point."_ Record as Partial completion.
- Record errors (incorrect paths, wrong inputs requiring correction), hesitations (pause >5s without action), and verbalisations (frustration, confusion, satisfaction).

### After the Session

- Thank the participant.
- Hand them the SUS questionnaire (paper or Google Form link).
- After SUS is complete, conduct probe questions (from `docs/task02/probe-questions-T1.md`).
- Do not debrief about the task intent until all probe questions are answered.

## Part 8 — Evaluation Measures & Data to Collect

### Performance Metrics (Objective)

| Metric               | Definition                                                                                          | How Measured                        |
| -------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------- |
| **Task Success**     | Completed / Partial / Failed — see `task-scenario-T1.md` for exact success level definitions        | Facilitator judgment at task end    |
| **Time on Task**     | Seconds elapsed from task start (participant reads task) to task end (goal achieved or abandoned)   | Stopwatch; note start + end time    |
| **Error Count**      | Number of incorrect navigation paths, wrong inputs, or mistaken form submissions requiring recovery | Facilitator tally mark per incident |
| **Hesitation Count** | Number of pauses >5 seconds with no mouse movement, click, or verbalisation                         | Facilitator tally mark per incident |

> **Error definition:** An error is any action the participant must undo, correct, or recover from. Deliberate exploration (hovering over options to read labels) is **not** an error. Submitting the form with missing required fields and then correcting them **is** an error.

> **Hesitation definition:** A pause of >5 seconds where the participant has stopped interacting with the screen and is not speaking. Note the approximate screen/section where the hesitation occurred.

### Preference Metrics (Subjective)

| Instrument          | Description                                  | When Administered            |
| ------------------- | -------------------------------------------- | ---------------------------- |
| **SUS**             | 10-item System Usability Scale (Brooke 1996) | After all tasks are complete |
| **Probe Questions** | 4 open questions for Task T1                 | After SUS, during debrief    |

### Data to Collect per Session

All data is recorded in the participant's `P{n}-session.md` file.

## Part 9 — Report Contents

The Usability Report (`docs/task02/usability-report.md`) will include:

1. **Executive Summary** — What was tested, who participated, key results in plain language.
2. **Methodology Overview** — Test type, format, participant profile, instruments used.
3. **Participant Table** — 5 participants with masked contacts.
4. **Task Scenario** — Full text of T1 and success criteria.
5. **Performance Metrics Summary Table** — Success rate, mean time, mean errors, mean hesitations across all 5 participants.
6. **SUS Scores Table** — Individual and group mean, adjective rating (Sauro & Lewis 2012).
7. **Findings** — Ranked by criticality (Nielsen severity 0–4 × frequency), with screenshot evidence per finding.
8. **Prioritised Recommendations** — Concrete, actionable fixes linked to finding IDs.
9. **Limitations** — Sample size, session format constraints, any missing data.
10. **Appendix A** — Paths to raw session notes (P1–P5).
11. **Appendix B** — Raw SUS responses.
