## Why Engine-Based Prioritisation?

The most critical dimension in compatibility testing is the **rendering engine**, not the browser brand. Chrome, Edge, and Chrome for Android all use Blink — finding a bug in any one covers all three. By contrast, Safari (WebKit) and Firefox (Gecko) have distinct rendering behaviours that Blink cannot reproduce.

> **iOS note:** iOS Safari was excluded from this run because iOS is not in `os_list`. macOS Safari (WebKit) is therefore the **only** WebKit coverage available and is promoted to Tier 1a as a result.

## Priority Tier 1a — WebKit (Test First)

> **Rationale:** iOS Safari is the canonical highest-risk test, but it is not available in this run. macOS Safari is the only WebKit cell, making it the highest priority to capture the WebKit rendering path before anything else.

### Order 1 — macOS / Safari / Desktop / A2 (Add/Edit Event Form)

- **Engine:** WebKit
- **Rationale:** A2 is the highest-complexity screen. Safari has known divergences in date picker UI (the native macOS date picker appears instead of the site's custom widget), file-upload dialog behaviour, form validation styling (Safari removes custom focus rings on inputs), and Rich-Text Editor rendering. Test this first to catch the highest-yield defects.
- **Specific risk areas:** date/time picker display, file upload button, RTE toolbar icon rendering, required-field asterisk alignment, Save Draft vs Publish button styles.

### Order 2 — macOS / Safari / Desktop / A4 (Participants & Reviews Approval)

- **Engine:** WebKit
- **Rationale:** Progress bar styling is a known WebKit difference (`-webkit-progress-bar` vs native). Tab panel underline/active indicator may differ. Status badge border-radius and padding can vary. Export button confirm dialog focus ring may be missing.
- **Specific risk areas:** progress bar fill colour and border, tab active indicator, badge border, confirmation dialog button focus ring.

### Order 3 — macOS / Safari / Desktop / A1 (Events List)

- **Engine:** WebKit
- **Rationale:** Table/list layout is generally stable in Safari but status badge colours and filter tab appearance may differ. Notification dot positioning uses `position: absolute` which can shift in WebKit. Sidebar rendering completes the WebKit full-session test.
- **Specific risk areas:** status filter tab underline, notification dot position, sidebar active-item highlight, action button hover colour.

## Priority Tier 1b — Gecko and Samsung Internet (Test Second)

> **Rationale:** Firefox (Gecko) is the only non-Blink, non-WebKit engine in common use. Samsung Internet (Blink†) has Samsung-specific behaviour on top of Chromium that can produce unique rendering artefacts, especially on mobile. Both are high-priority because they cover rendering paths entirely absent from the Blink cells.

### Order 4 — Android / Firefox / Tablet / A2 (Add/Edit Event Form)

- **Engine:** Gecko
- **Rationale:** A2 is highest complexity; Firefox's form rendering is the most distinct from Blink — date picker shows a native Firefox calendar widget instead of the EMS custom picker, file upload button loses custom styling, and RTE uses a different `contenteditable` rendering path. Tablet viewport also tests the two-column form layout collapse behaviour.
- **Specific risk areas:** native Firefox date picker appearing, file upload button width, RTE minimum height at 768px, Save Draft/Publish button side-by-side layout at tablet width.

### Order 5 — Android / Firefox / Tablet / A4 (Participants & Reviews Approval)

- **Engine:** Gecko
- **Rationale:** Tab panels at tablet width often trigger a CSS breakpoint that may overflow or collapse. Firefox's `<progress>` element does not support WebKit/Blink vendor prefixes, so progress bar styling may revert to the browser default (grey). Status badge padding differs slightly in Gecko.
- **Specific risk areas:** tab overflow at 768px, progress bar default grey fill, badge border-radius, Export button tooltip.

### Order 6 — Android / Firefox / Tablet / A1 (Events List)

- **Engine:** Gecko
- **Rationale:** Data table layout at tablet width is a known responsive risk. Filter tabs at 768px may overflow horizontally. Notification dots rely on `background-color` + `border-radius` which behaves consistently in Gecko but should be verified.
- **Specific risk areas:** table column overflow at tablet, filter tab scrollability, action button tooltip on hover.

### Order 7 — Android / Samsung Internet / Phone / A2 (Add/Edit Event Form)

- **Engine:** Blink†
- **Rationale:** Samsung Internet on Android renders form controls using Samsung-specific UI chrome (e.g., custom input styling). At 390×844 the form collapses to single column — verify no horizontal overflow, no overlapping labels, and that the image upload dropzone remains visible. Date pickers on Android open a native OS date dialog, which may conflict with EMS's custom date picker JS.
- **Specific risk areas:** date picker OS dialog override, file upload dropzone collapse at 390px, RTE toolbar icon overflow on single-column layout, Submit buttons at bottom visible without horizontal scroll.

### Order 8 — Android / Samsung Internet / Phone / A4 (Participants & Reviews Approval)

- **Engine:** Blink†
- **Rationale:** Tab panels at 390px are a critical risk — they commonly overflow horizontally or collapse into a dropdown. Samsung Internet may apply additional text scaling that pushes badge labels out of their containers. Progress bar may use Samsung's custom Chromium theming.
- **Specific risk areas:** tab panel horizontal overflow / dropdown fallback, badge text overflow at small size, progress bar Samsung theming, Export button touch target size.

### Order 9 — Android / Samsung Internet / Phone / A1 (Events List)

- **Engine:** Blink†
- **Rationale:** The Events List table at phone width is likely to collapse — verify each row's data is still legible and action buttons (Edit, Delete) are not obscured. Notification dots may be too small for touch target. Samsung Internet's default font scaling may cause text overflow.
- **Specific risk areas:** table row collapse / card layout at 390px, action button touch target, notification dot visibility, status badge readability.

## Priority Tier 2 — Blink / Edge Desktop (Test Third)

> **Rationale:** Edge is the user's own local browser on Windows 11 and is the closest to the developer baseline. Testing these cells validates the expected admin experience but is unlikely to reveal new defects not already caught by Firefox and Safari cells.

### Order 10 — Windows / Edge / Desktop / A2 (Add/Edit Event Form)

- **Engine:** Blink
- **Rationale:** Baseline desktop form test. Edge is used by the tester locally, making this a reference cell. Also confirms BrowserStack's Edge session matches the tester's local environment.
- **Specific risk areas:** Same as baseline — verify no regressions from the BrowserStack session configuration itself.

### Order 11 — Windows / Edge / Desktop / A4 (Participants & Reviews Approval)

- **Engine:** Blink
- **Rationale:** Validates participant management in the most likely real admin environment (Windows + Edge). Export to Excel functionality is worth verifying as a file download trigger differs across environments.
- **Specific risk areas:** Excel download trigger, confirmation dialog rendering, tab active indicator.

### Order 12 — Windows / Edge / Desktop / A1 (Events List)

- **Engine:** Blink
- **Rationale:** Establishes a Blink/Windows desktop baseline for the Events List. Lowest risk cell in the entire matrix.
- **Specific risk areas:** Overall layout integrity, sidebar consistency.

## Priority Tier 3 — Blink / Android Chrome Phone (Test Last)

> **Rationale:** Chrome on Android is Blink — the same engine as Windows/Edge. These cells add Android-specific touch interaction coverage but are unlikely to reveal new rendering defects not already found in Samsung Internet cells.

### Order 13 — Android / Chrome / Phone / A1 (Events List)

- **Engine:** Blink (mobile)
- **Rationale:** Validates the Events List on stock Android Chrome at 390×844. Checks touch target sizes for action buttons and filter tabs.
- **Specific risk areas:** Row card layout at 390px, touch target on action buttons.

### Order 14 — Android / Chrome / Phone / A2 (Add/Edit Event Form)

- **Engine:** Blink (mobile)
- **Rationale:** Validates the form at 390×844 on stock Android Chrome. Focus on whether the OS date picker overrides the EMS custom picker and whether image upload works.
- **Specific risk areas:** OS date picker override, image upload on mobile Chrome, virtual keyboard pushing form layout.

### Order 15 — Android / Chrome / Phone / A4 (Participants & Reviews Approval)

- **Engine:** Blink (mobile)
- **Rationale:** Final cell. Validates tab panel and badge rendering on stock Android Chrome phone. Closes out all 15 planned cells.
- **Specific risk areas:** Tab overflow, badge readability, progress bar at 390px.

## Recommended BrowserStack Session Order

Group tests by BrowserStack session (one session = one OS/browser/device configuration) to minimise session setup overhead. Within each session, test all three screens before closing.

```
Session 1:  macOS / Safari / Desktop     → test A2 → A4 → A1   (orders 1–3)
Session 2:  Android / Firefox / Tablet   → test A2 → A4 → A1   (orders 4–6)
Session 3:  Android / Samsung Internet / Phone → test A2 → A4 → A1  (orders 7–9)
Session 4:  Windows / Edge / Desktop     → test A2 → A4 → A1   (orders 10–12)
Session 5:  Android / Chrome / Phone     → test A1 → A2 → A4   (orders 13–15)
```

> **Reminder:** Within each BrowserStack session, open each screen URL in a **fresh tab**. Do not navigate between screens in the same tab — state from A2's form may persist and affect A4's page load.
